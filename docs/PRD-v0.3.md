## 1. 项目背景与定位

### 1.1 业务背景

排水管网监测数据的人工分析存在三个痛点:
- **耗时**: 单个监测项目通常涉及数十个点位,每个点位需要逐日检查数据质量、识别排污规律、评估运行风险,人工分析一份完整报告需要数天
- **重复**: 不同项目的分析流程高度相似,但每次都要从头做一遍
- **依赖经验**: 排污规律判断、数据异常归因等环节强依赖工程师经验,难以标准化

本项目将这套人工分析流程改造为**"规则模块 + LLM 模块"混合架构的自动化 Pipeline**,从原始 CSV 数据到最终 Word 分析报告端到端自动生成,中间设计 3 个人工介入点用于关键决策。

### 1.2 项目定位

本项目同时承担三重目标:

| 目标 | 衡量标准 |
|------|---------|
| **工程化锻炼** | 完整走完 PRD → 架构 → 测试 → 文档 → 重构的工程流程 |
| **业务功能完整** | 6 个核心模块全部交付,端到端可运行,产出合格 Word 报告 |
| **简历项目价值** | 架构清晰可讲解,LLM 使用边界有明确判断依据,工程化痕迹完整 |

**主目标是"端到端跑通,产出合格报告"**。工程化是"做事的方式",不是目的本身。

### 1.3 项目历史与本次目标

本项目已存在两个并行实现:
- `sewage_monitoring/`: 第一版,有完整集成能力(Orchestrator、LLM 客户端、配置管理),但缺独立 `dry_analysis` 模块
- `pipeline/`: 第二版,模块边界清晰,但缺总入口编排器、缺 LLM 集成、缺 `risk_analysis` 模块

本次目标:**以 `pipeline/` 的模块边界为目标架构,合并 `sewage_monitoring/` 的集成能力,统一为单一代码主线**,同时解决现有的产品质量问题(报告错位、字段映射错误等)。

## 2. 术语表

为避免概念混淆,本项目使用以下严格定义的术语:

| 术语 | 定义 | 在本项目的体现 |
|------|------|---------------|
| **Pipeline** | 由多个模块按固定顺序组成的数据处理流程 | 整个排水分析流程 |
| **Module(模块)** | 完成单一职责的代码单元,可以是纯规则、也可以含 LLM 调用,但**没有自主决策循环** | 数据筛选、降雨分析等模块 |
| **Agent** | LLM 驱动的、有循环判断能力、能主动使用工具的单元 | v1 中**没有真正的 Agent**;v2 可能引入诊断助手 Agent |
| **人工介入点** | Pipeline 暂停、等待人工决策、然后继续的位置 | v1 共 3 处 |

**重要原则**:基于规则跑的代码,不命名为 `XxxAgent`,统一改为 `XxxModule`。

## 3. 范围定义

### 3.1 v1 范围(本次必做)

**功能模块**:

| # | 模块名 | 主要职责 | 是否含 LLM | 结果是否进 Word 报告 |
|---|--------|---------|-----------|---------------------|
| 1 | 数据筛选 (data_filter) | 筛选有效旱天数据 | ❌ | 不直接进(供后续使用) |
| 2 | 旱天分析 (dry_analysis) | 旱天流量统计 | ❌ | ✅ |
| 3 | 降雨分析 (rainfall_analysis) | 降雨日识别、场次划分、等级评定 | ❌ | ✅ |
| 4 | 雨天事件统计 (event_stats) | 选定降雨场次下各点位统计计算 | ❌ | ❌(辅助计算,共享给 RDII 和风险分析) |
| 5 | RDII 分析 (rdii_analysis) | 降雨入流入渗计算 | ❌ | ❌(辅助计算,不进报告) |
| 6 | 风险分析 (risk_analysis) | 旱天风险 + 雨天溢流风险评估 | ❌ | ✅ |
| 7 | 排污规律分析 (pattern_analysis) | 流量曲线特征识别与分类 | ✅ | ✅ |
| 8 | 报告组装 (report_assembler) | 填充 Word 模板生成最终报告 | ✅ | (本身就是报告输出) |

**关于"雨天事件统计"的说明**: 这是一个独立的内部计算步骤(不一定单独成模块,可作为公共工具函数),从原 `analyze_event_flow.py` 沿袭逻辑(已合并到 `rdii_analysis/analyzer.py`)。本次抽出来,作为 RDII 分析和风险分析 Part 2(雨天溢流风险)的共享输入。具体落地形式在架构阶段确认。

**工程化要求**(贯穿全程):
- 统一代码主线,删除冗余的 `sewage_monitoring/` 和 `_archive_old_agents/`
- 报告组装模块有单元测试覆盖核心逻辑;其他模块的现有测试保留,不强制扩充
- README 完整,新用户能照着跑通
- 数据与代码分离(`data/` 进 `.gitignore`,`data_sample/` 进 git)
- Git 提交规范化(Conventional Commits + 中文描述)
- 2-3 个核心决策写 ADR(配置选 Excel、LLM 边界、代码主线合并方案)

### 3.2 明确不做的功能(暂列,可能未来再考虑)

以下功能本项目**不做**,在开发中不要临时扩展:

- **排污规律案例库构建**(v1 用现有 LLM 实现观察效果,效果不佳再考虑案例库)
- **排污规律置信度机制**(v1 LLM 输出判断和理由,不输出置信度)
- **降雨入流模块进入报告**(v1 只计算,结果在 xlsx 中)
- **诊断助手 Agent**
- **报告校对 Agent**
- **多点位拓扑关系分析**
- **Web UI / GUI**
- **持续数据接入 / 定时跑**
- **模块级并行执行**(架构按 DAG 设计,但 v1 全部串行)
- **对外展示物深度建设**(复盘文章、样例数据等)——v1 完成后再决定是否做
- **ADR 全套**(只做核心 2-3 个,其他推到 v2)

### 3.3 明确不做(永久,非 v2)

- 不做实时监控告警系统
- 不做多用户协作功能
- 不做云端部署服务化

## 4. 用户与使用场景

### 4.1 用户

**主要用户**: 项目作者本人,具备 Python 环境、能在命令行操作。

**次要用户**: 排水行业同事,具备 Excel 操作能力,但不一定熟悉命令行——因此 Pipeline 的人工介入点必须通过 **Excel 文件交互**,而不是命令行问答。

### 4.2 典型使用场景

```
1. 用户准备数据:
   - 各点位监测 CSV 文件 → data/flow/
   - 降雨数据 CSV → data/rainfall.csv
   - 点位元信息 xlsx → data/点位信息.xlsx

2. 用户填写配置:
   - 在 data/baseinfo.xlsx 中填写项目信息、分析参数

3. 用户启动 Pipeline:
   - python run.py
   
4. Pipeline 检查 outputs/ 下是否已有筛选结果:
   - 有 → 命令行提示:"检测到已有筛选结果,是否直接使用?(y/n)"
     - y → 跳过筛选,直接进入第 7 步
     - n → 重新跑筛选
   - 无 → 进入第 5 步

5. Pipeline 执行数据筛选模块
   - 输出: outputs/筛选结果.xlsx(可用天标颜色)

6. 介入点 1: 用户审核筛选结果
   - 用户打开 Excel,通过修改单元格颜色调整"可用/不可用"
   - 保存关闭
   - 命令行提示: "数据筛选完成,请审核 outputs/筛选结果.xlsx,完成后输入 y 继续:"

7. Pipeline 执行降雨分析
   - 输出: 综合分析结果.xlsx 的"降雨日统计"、"降雨场次"、"降雨概况" sheet
   - 输出: outputs/降雨分析图/ 下的时间序列图、占比饼图

8. 介入点 2: 用户选择降雨场次
   - 命令行提示: "降雨分析完成,请在 baseinfo.xlsx 的'降雨场次选择' sheet 中填写选中的场次编号,完成后输入 y 继续:"
   - 用户参考"降雨场次"sheet(含等级列),在 baseinfo.xlsx 中填写选中编号

9. Pipeline 执行后续分析:
   - 旱天分析
   - 雨天事件统计(独立内部步骤)
   - RDII 分析(基于雨天事件统计)
   - 排污规律分析

10. 介入点 3: 用户审核排污规律 LLM 判断
    - 命令行提示: "排污规律分析完成,请审核综合分析结果.xlsx 的'排污规律分析' sheet,完成后输入 y 继续:"
    - 用户修改 LLM 误判的行

11. Pipeline 执行风险分析:
    - Part 1: 旱天风险(淤积、运行、溢流风险)
    - Part 2: 雨天溢流风险(基于雨天事件统计 + 点位信息)

12. Pipeline 执行报告组装

13. 最终交付:
    - outputs/分析报告.docx (Word 报告)
    - outputs/综合分析结果.xlsx (所有中间数据)
    - outputs/筛选结果.xlsx (筛选审核记录)
    - outputs/降雨分析图/ (降雨相关图表)
    - outputs/排污规律图/ (排污规律曲线图)
```

## 5. 功能需求详述

### 5.1 数据筛选模块 (data_filter)

**输入**:
- 各点位监测 CSV(字段: 数据时间、流量、流速、液位)
- 降雨数据 CSV
- 配置参数(来自 baseinfo.xlsx 和 config.yaml): 缺失率阈值、雨天剔除阈值、IQR 因子等

**核心逻辑**:
- **沿用现有代码的筛选规则**(经过多版调优,不重写):
  - 剔除缺失率高于阈值的天
  - 剔除雨天(日降雨量 ≥ 阈值)
  - 剔除流量异常天(IQR 异常值检测 + 高零值比例检测)

**输出**:
- `outputs/筛选结果.xlsx`(独立文件,不进综合 xlsx)
- **沿用现有输出格式**(可用天用颜色标记),供人工审核

**复用机制**:
- Pipeline 启动时,先检查 `outputs/筛选结果.xlsx` 是否已存在
- 已存在 → 命令行询问"检测到已有筛选结果,是否直接使用?(y/n)"
  - y → 跳过筛选,直接读取该文件作为筛选结果
  - n → 重新跑筛选,覆盖旧文件

**人工介入(介入点 1)**:
- 用户打开 `outputs/筛选结果.xlsx`,通过修改单元格颜色调整"可用/不可用"标记
- 保存关闭后,在命令行输入 y 继续
- Pipeline 后续模块重新读取该文件,以用户修改后的颜色为准

---

### 5.2 旱天分析模块 (dry_analysis)

**输入**: 筛选后的有效旱天数据

**核心逻辑**: 计算旱天流量、液位、流速的基础统计(日均、最大、最小、变异系数等)

**输出**: 
- `综合分析结果.xlsx` 的 `旱天分析` Sheet
- 不画图,结果主要作为风险分析、报告组装的输入

---

### 5.3 降雨分析模块 (rainfall_analysis)

**输入**: 降雨时间序列数据

**核心逻辑**:
- 识别降雨日
- 按"前后无降雨间隔 X 小时"标准划分降雨场次(**X 从 baseinfo.xlsx 读取,默认 12 小时**)
- 统计每场次的总降雨量、峰值雨强、降雨历时
- **按气象局《降水量等级》GB/T 28592-2012 标准评定降雨等级**(小雨/中雨/大雨/暴雨/大暴雨/特大暴雨)
- 统计监测期内总天数、降雨日数、非降雨日数

**数据输出**(进入 `综合分析结果.xlsx`):
- **Sheet: 降雨日统计** —— 列 1 时间(日期),列 2 当日降雨量(mm)
- **Sheet: 降雨场次** —— 每场降雨一行,含起止时间、总降雨量、峰值雨强、降雨历时、**降雨等级**(最后一列)
- **Sheet: 降雨概况** —— 监测总天数、降雨日数、非降雨日数(数值表)

**图表输出**(`outputs/降雨分析图/`):
- **图 1: 日降雨量时间序列条形图** —— 横轴时间(天),纵轴当日降雨量(mm)
- **图 2: 降雨日占比饼图** —— 降雨日 vs 非降雨日,带百分数标注

**人工介入(介入点 2)**:用户参考"降雨场次"sheet(含等级列),在 `baseinfo.xlsx` 的"降雨场次选择"sheet 中**填写选中场次的编号**,Pipeline 后续读取这些编号匹配对应记录。

**进入报告的内容**: 降雨概况数据 + 两张图,进入 Word 报告的"降雨情况分析"章节。

---

### 5.4 雨天事件统计(独立内部计算步骤)

**说明**: 这不是一个对外暴露的"模块",而是一个**内部计算步骤**,作为 RDII 分析和风险分析 Part 2(雨天溢流风险)的共享输入。具体落地形式(独立模块 / 公共工具函数 / 嵌入某个模块)在架构阶段确认。

**历史关系**: 沿袭原 `analyze_event_flow.py` 的逻辑,该逻辑此前合并在 `pipeline/rdii_analysis/analyzer.py` 中。本次将其抽出,避免 RDII 和风险分析重复计算。

**输入**:
- 用户选定的降雨场次(来自 baseinfo.xlsx)
- 降雨结束后影响延迟参数(来自 baseinfo.xlsx,默认 48 小时)
- 各点位在选定降雨场次期间(及延迟时间内)的监测数据

**核心逻辑**: 对每个点位 × 每场选定降雨,统计该事件期间的关键指标

**输出统计指标**(每个点位 × 每场降雨 → 一组统计值):
- 最大液位
- 平均液位
- 平均流量
- 平均流速
- 最大流量

**输出位置**:
- `综合分析结果.xlsx` 的 `雨天事件统计` Sheet —— 用于综合评估降雨对管道的影响
- **不进 Word 报告**(仅作为 xlsx 中的参考数据)

**下游使用**:
- **RDII 分析**: 使用流量相关指标计算入流入渗系数
- **风险分析 Part 2**: 使用最大液位结合点位井深计算溢流风险

---

### 5.5 RDII 分析模块 (rdii_analysis) ⚠️ 辅助模块

**输入**: 旱天数据 + 雨天事件统计结果 + 选定的降雨场次

**核心逻辑**: 计算每场降雨的入流入渗量、入流入渗系数

**输出**: 
- `综合分析结果.xlsx` 的 `RDII 分析` Sheet
- `outputs/RDII 分析图/` 下的 RDII 过程图(每场降雨/每个点位一张,具体形态沿用现有代码逻辑)

**重要说明**: 
- **本模块所有输出(包括 Sheet 和图)均不进入 Word 报告**
- 理由: RDII 完整分析需要人工根据管网拓扑关系做进一步处理,自动化产出的结果仅作为辅助参考

---

### 5.6 风险分析模块 (risk_analysis)

**说明**: 本模块分两个部分(Part 1 旱天风险 + Part 2 雨天溢流风险),两部分都进入 Word 报告。

**执行位置**: 介入点 3 之后(因为 Part 2 依赖雨天事件统计结果,且为确保所有前置数据准备齐全)。

#### Part 1: 旱天风险

**输入**: 旱天分析结果 + 点位元信息

**核心逻辑**: 基于阈值规则,评估每个点位的淤积风险、运行风险、溢流风险等级(具体计算规则在模块代码中实现,不在 PRD 详述)

**输出**: 
- `综合分析结果.xlsx` 的 `旱天风险` Sheet
- 表格结构: 点位名 | 管径 | 井深 | 淤积风险 | 运行风险 | 溢流风险
- 每个点位一行

**进入报告**: 对应 Word 报告的 **3.2.1 旱天运行风险分析** 章节

#### Part 2: 雨天溢流风险

**输入**: 雨天事件统计结果(最大液位)+ 点位元信息(井深、管径)

**核心逻辑**: 基于每个点位在每场选定降雨下的最大液位,结合井深,评估溢流风险值和等级(具体计算规则在模块代码中实现)

**输出**:
- `综合分析结果.xlsx` 的 `雨天溢流风险` Sheet
- 表格结构: 点位名 | 管径 | 井深 | [场次1风险值][场次1风险等级] | [场次2风险值][场次2风险等级] | ...
- 每个点位一行,各场降雨作为列展开
- 不做可视化

**进入报告**: 对应 Word 报告的 **3.2.2 雨天运行风险分析** 章节

---

### 5.7 排污规律分析模块 (pattern_analysis) ✅ 含 LLM

**输入**: 筛选后的有效旱天数据(分钟级,每个点位)

**核心逻辑**:

**Step 1 - 数据预处理**:
- 对每个点位,把所有有效旱天的同一时刻数据做平均
- 得到代表一天 24 小时的分钟级均值序列(1440 个点)

**Step 2 - 平滑**:
- 用平滑窗口参数做移动平均(**参数来自 baseinfo.xlsx,默认 20 分钟**)

**Step 3 - 画图**:
- 用 matplotlib 画排污规律特征曲线图
- 输出: `outputs/排污规律图/<点位编号>_规律图.png`

**Step 4 - 特征提取**:
- 在平滑后的曲线上计算结构化特征
- 例: 早高峰时间、晚高峰时间、Kz 时变化系数、双峰分离度、平坦度、工作日/周末差异等

**Step 5 - LLM 判断**:
- 构造 prompt: 包含上一步的特征值 + 设计好的判断指引
- LLM 输出: 分类(典型生活污水/工业排放/混排/异常等) + 判断理由
- **v1 不做案例库**(保留现有 LLM 实现观察效果)
- **v1 不做置信度机制**

**数据输出**(进入 `综合分析结果.xlsx`):
- **Sheet: 排污规律分析** —— 点位编号、判断、理由、特征值、图路径

**图表输出**(`outputs/排污规律图/`):
- 每个点位一张曲线图

**人工介入(介入点 3)**:用户审核 `综合分析结果.xlsx` 的"排污规律分析" sheet,修改 LLM 误判的行,在命令行输入 y 继续。

**进入报告**: 排污规律分类结果 + 曲线图,进入 Word 报告的"排污规律分析"章节。

**v1 重点关注**:
- 现有 LLM 实现的效果观察(准确率大概多少、错在哪类点位)
- 为 v2 案例库改造积累数据(把误判案例记录下来)

---

### 5.8 报告组装模块 (report_assembler) ✅ 含 LLM

**输入**: 
- 上述所有模块的输出(综合分析结果.xlsx)
- Word 模板(`监测数据分析报告模板.docx`)
- **点位信息**(`data/点位信息.xlsx`,独立原始数据,不在 baseinfo 中)
- 排污规律图、降雨分析图

**核心逻辑**:

**Step 1 - 模板字段映射**:
- 解析 Word 模板,识别所有占位符(段落字段、表格字段)
- 维护字段映射表(占位符 → 数据源)

**Step 2 - 数据填充**:
- 按映射表把分析结果填入对应位置
- 处理表格、段落、图表插入
- 从点位信息.xlsx 直接提取生成"点位概况"章节内容

**Step 3 - LLM 生成自然语言小结**:
- 对每个章节,LLM 生成一段通顺的中文小结
- 例如:"本项目共监测 X 个点位,数据质量整体..."、"X 个点位呈现典型生活污水规律,Y 个点位..."

**Step 4 - 输出**:
- `outputs/分析报告.docx`(最终交付)

**当前痛点(v1 必须解决)**:
- ❌ 字段填错位置(模板字段映射有问题)
- ❌ 视觉错位(填对了字段但格式乱了)
- ❌ 生成文字不通顺(LLM prompt 需要优化)

**验收**:
- 给定标准测试数据,生成的报告与人工填充的模板视觉一致
- 所有字段填充位置正确
- LLM 生成的小结通顺、用词专业

## 6. LLM 使用边界(核心设计决策)

本项目在 LLM 使用上遵循一个明确原则:

> **LLM 仅用于"规则拿不到的输入"或"规则不擅长的输出"。**

### 6.1 用 LLM 的环节及理由

| 环节 | LLM 拿到的输入 | LLM 的不可替代性 |
|------|--------------|----------------|
| 排污规律分析 | 数值特征 + 判断指引 | 规则无法完整表达"看图说话"的专家经验,LLM 基于特征做综合判断 |
| 报告小结生成 | 结构化分析结果 | 规则模板能拼接,但**生成通顺自然语言**是 LLM 强项 |

### 6.2 不用 LLM 的环节及理由

| 环节 | 不用 LLM 的原因 |
|------|---------------|
| 数据筛选 | 纯数值阈值判断,LLM 拿到的输入跟规则一样,且不如规则稳定 |
| 旱天分析 | 纯统计计算 |
| 降雨分析 | 纯规则(降雨日识别、场次划分、等级评定有国标) |
| RDII 分析 | 纯数值计算 |
| 风险分析 | 纯阈值规则评分 |

### 6.3 LLM 调用的工程化要求

- **统一 LLM 客户端**: 所有 LLM 调用走统一客户端模块,不在业务模块里直接调 API
- **prompt 版本化**: prompt 模板存为单独文件,版本化管理
- **失败兜底**: LLM 调用失败时,模块输出"LLM 失败,需人工处理",不让 Pipeline 崩溃
- **可关闭**: config.yaml 中提供 `llm.enabled: false` 开关,关闭后规律分析输出"未分类"、报告小结使用模板拼接兜底

## 7. 非功能性需求

### 7.1 性能

- 处理 30 个点位 × 90 天数据,端到端运行时间 ≤ 30 分钟(LLM 调用占大头)
- v1 不要求并发,串行执行即可
- 内存占用 ≤ 4GB(普通笔记本可跑)

### 7.2 可靠性

- 任一模块失败,Pipeline 输出明确错误信息,不静默失败
- LLM 调用必须有重试机制(最多 3 次,指数退避)
- 中间结果落盘,失败后可从最近模块的输出恢复

### 7.3 可维护性

- 每个模块独立可测试(单元测试 + 模块级 CLI)
- 配置与代码分离(baseinfo.xlsx + config.yaml + .env)
- 数据与代码分离(.gitignore 排除 data/)
- 关键参数(阈值、模型名)不硬编码

### 7.4 可演进性

- **架构按 DAG 思想设计**: 模块之间的依赖关系明确,默认串行执行,但任意能并行的环节都可以并行化(v1 不做)
- v2 引入 Agent 时,现有模块能作为 Tool 被复用
- 新增分析模块时,只需实现统一接口、注册到 Orchestrator,不动其他模块

### 7.5 可解释性

- 每个模块的判断都有"理由字段"或"日志记录"
- 关键决策(为什么用 LLM、为什么用这些阈值)记录在 `docs/decisions/` 目录(ADR)
- v1 只做 2-3 个核心 ADR

## 8. 配置文件结构

本项目采用**三层配置**设计:

### 8.1 用户层: `data/baseinfo.xlsx`

由用户填写,Excel 友好,同事可改:

```
Sheet: 项目基本信息
  - 项目名称、监测起止时间、报告标题、撰写人等

Sheet: 分析参数
  - 排污规律平滑窗口(分钟): 默认 20
  - 降雨场次划分间隔(小时): 默认 12
  - 降雨结束后影响延迟(小时): 默认 48(用于 RDII 和雨天事件统计)
  - 其他阈值参数(缺失率阈值、雨天阈值、IQR 因子等,可有默认值)

Sheet: 降雨场次选择(介入点 2 后填写)
  - 用户填写选中场次的编号(逗号分隔或一列多行)
  - 程序读取这些编号,匹配"降雨场次"sheet 里的对应记录
```

### 8.2 技术层: `config.yaml`

由开发者维护,用户基本不改:

```yaml
input:
  flow_data_dir: "data/flow/"
  rainfall_data_path: "data/rainfall.csv"
  site_meta_path: "data/点位信息.xlsx"
  baseinfo_path: "data/baseinfo.xlsx"
  report_template_path: "data/监测数据分析报告模板.docx"

output:
  output_dir: "outputs/"

llm:
  enabled: true
  provider: "deepseek"
  model: "deepseek-chat"

pipeline:
  pause_after_filter: true        # 介入点 1
  pause_after_rainfall: true      # 介入点 2
  pause_after_pattern: true       # 介入点 3
```

### 8.3 密钥层: `.env`(不进 git)

```
DEEPSEEK_API_KEY=...
DEEPSEEK_BASE_URL=...
```

### 8.4 输出文件结构

```
outputs/
├── 筛选结果.xlsx          # 数据筛选输出,介入点 1 交互文件(独立)
├── 综合分析结果.xlsx       # 所有其他模块结果汇总
│   ├── Sheet: 旱天分析
│   ├── Sheet: 降雨日统计
│   ├── Sheet: 降雨场次
│   ├── Sheet: 降雨概况
│   ├── Sheet: 雨天事件统计
│   ├── Sheet: RDII 分析
│   ├── Sheet: 旱天风险
│   ├── Sheet: 雨天溢流风险
│   └── Sheet: 排污规律分析
├── 降雨分析图/             # 降雨相关图表
│   ├── 日降雨量时间序列图.png
│   └── 降雨日占比饼图.png
├── 排污规律图/             # 每个点位一张曲线图
│   └── <点位编号>_规律图.png
```
